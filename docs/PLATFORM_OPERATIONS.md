# Online edition operations and rollback

The canonical offline guest URL remains `http://localhost/holdem-lab/`. Online staging uses a separate loopback origin, `http://127.0.0.1:4318/holdem-lab/`; browser storage is separate. The source and database are never copied into Apache. Apache's existing local-only guard stays intact.

`scripts/Start-POK-Online.ps1` requires the built `online-dist` directory, verifies that port 4318 is free or belongs to the recorded project process, launches only this Node entry point hidden, and waits for its real health response. It generates a dedicated local auth secret in `.pok-local/auth.secret`, creates `.pok-local/pok.sqlite`, and exposes an explicitly labelled local mail-test inbox. It never kills a port occupant. `scripts/Stop-POK-Online.ps1` compares the recorded PID, Node process name, absolute entry-point command line and start time before stopping only the owned process. Neither script changes services, firewall, global PATH, XAMPP or the offline browser notebook.

The main process binds only `127.0.0.1`. `POK_PORT` may select another verified free loopback port for isolated tests. `POK_DATA_DIR` and `POK_PUBLIC_DIR` separate private runtime state and public assets; the latter defaults to `online-dist`. Use one project launcher rather than an unrelated permanent server. The test sink is impossible to enable in `NODE_ENV=production`; production also refuses missing SMTP, missing dedicated auth secret and non-HTTPS canonical origins.

Owner bootstrap is a local operator action, not a first-registrant rule. Register, verify and sign in an isolated member, copy its user ID from its own account export, and use `server/operator.ts bootstrap-owner <verified-user-id>` through the installed project Node/tsx runtime. The command refuses an existing owner, unverified account, and production account without MFA. It creates no password and accepts no email identity shortcut. Reauthenticate before sensitive CP actions. Additional roles are granted by an existing owner with a reason.

Private backups use `server/operator.ts backup <new-private-destination>` with Node's SQLite online-backup API. The command refuses overwriting, refuses an htdocs destination, and runs `PRAGMA integrity_check` on the copy. The real automated test creates a SQLite database in an isolated temporary directory, backs it up, verifies the audit fixture in the copy, checks restore preflight, and verifies overwrite refusal. `restore-check` only checks a candidate; it does not replace live data. A real production restore has NOT_RUN.

For rollback, stop only the owned online process; preserve its current private directory as a checkpoint. Verify a backup using `restore-check`, restore into a new private data directory, restore the matching auth secret through the secret manager, and select that directory using `POK_DATA_DIR`. Keep the prior directory intact until verification succeeds. Never copy only a live WAL-mode database file while discarding its WAL. Restore public assets/source from the matching private release and lockfile. The original HIL archives and local history are independent rollback points.

Production remains BLOCKED without an approved destination. The personal XAMPP workstation is not the production plan. At an approved host, use a supported Node runtime, project-local locked dependencies, private persistent SQLite volume, protected secret store, SMTP sender, HTTPS reverse proxy and backups. Run a single application instance for this SQLite design. Preserve exact Host and Origin, regenerate `X-Forwarded-Proto: https`, strip client-supplied forwarding headers, keep the app's loopback listener, enforce request/time limits, and serve only `online-dist` publicly. Do not expose database files, development inbox, source, `.git`, environment files, traces or logs. Bootstrap the owner offline and complete MFA before CP access. Check `/api/status`, account verification/recovery, backup/restore and all role boundaries before opening signup.

External setup checklist (all distinct from a private GitHub release): approved host/domain/TLS; production secret manager and backup retention; working SMTP with verified receipt; OAuth app registration/approval and exact callbacks for any enabled provider; live provider login/link/unlink validation; production location-policy adapter and explicit nonzero AI budget/key if coaching is desired; independent security and native-language/content review. No service purchase, public hosting, tunnel, real provider login or paid AI call is implied by these artifacts.
