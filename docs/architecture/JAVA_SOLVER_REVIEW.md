# Java river solver review

Checked 2026-09-30. This is a working experimental adapter to a real external solver, restricted to a small, fully specified heads-up river game. It is not a general Hold'em solution, a replacement for the offline poker engine, or a claim of professional playing strength.

## Provenance and implementation choice

The selected source is [TexasHoldemSolverJava](https://github.com/bupticybee/TexasHoldemSolverJava), pinned to `e90d1bb4c7cf6fbd433428d6acf41f606e0c8530`, whose commit date is `2021-11-29T11:56:23+08:00`. The actual [MIT license](https://github.com/bupticybee/TexasHoldemSolverJava/blob/e90d1bb4c7cf6fbd433428d6acf41f606e0c8530/LICENSE) is retained in `engine-adapters/java/notices/TexasHoldemSolverJava-MIT.txt`. The upstream README says development is no longer maintained. Its performance claims were not adopted as POK measurements.

Review covered the README, license, POM, card and range classes, tree nodes, CFR traversal, trainables, and best-response implementation. The old POM was not executed. Its obsolete Fastjson/Jackson/SnakeYAML dependencies were replaced by the four pinned runtime artifacts below for a selected headless compilation. No GUI, Python runner, resource dictionary, sample range, or Pio-labelled data is included in the adapter or study packs. The first research clone included upstream resources; no such sample was used to author the original POK scenarios. The reproducible download recipe uses a sparse checkout of Java source.

The real upstream `CfrPlusRiverSolver` traversal and `DiscountedCfrTrainable` regret/average-policy updates are used. Inspection found that `CfrPlusTrainable.getAverageStrategy()` and `CfrTrainable.getAverageStrategy()` return their current strategy even after calculating an average. Those classes are excluded. The chosen discounted trainable returns its accumulated average, with upstream parameters alpha 1.5, beta 0.5, gamma 2 and theta 0.9. This is disclosed as the upstream discounted variant; no unsupported theoretical convergence rate is claimed.

Only two upstream compatibility changes are generated by the build recipe: the `JSONObject` import moves to Fastjson2, and `GameTree` gains a constructor accepting an already validated in-memory tree. Original file-loading entry points are not exposed to requests. POK supplies the input boundary, river-tree builder, reference hand comparator, average-policy export, conditional EV calculation, and process guard. `PokBoundedSolver` invokes the original traversal directly rather than the original file-writing training runner. It replaces the constructor's unused executor with a one-thread executor; computation itself is single-threaded. JVM housekeeping is not counted as a compute thread.

## Supported model and exact meanings

The model has exactly two players, actor 0 out of position and actor 1 in position; exactly five public board cards; optional explicit dead cards; weighted concrete two-card combinations; a positive integer initial pot; and a common integer effective stack. Range weights represent the independent product distribution conditioned on both hands being compatible with each other and known cards. Per-seat proportional normalization does not change that distribution. The old solver stores normalized weights as floats, so small rounding differences remain. A hand with no compatible opponent hand is rejected rather than assigned an undefined belief.

The tree includes checks, configured integer bet sizes, folds, calls, and at most one configured **full** raise. `RAISE 150` means raise **to** 150 total chips invested on this river, not raise by 150. No short all-in raise is represented. Uncalled chips are returned. The public contract is narrower than the raw adapter: at most 32 combinations per seat, two bet sizes and one raise size; the raw boundary additionally enforces 128 combinations per seat and 96 public nodes. This is river-only: no future chance nodes, turn/flop solving, rake, side pots, tournament model, multiway game, or omitted bet sizes are solved.

Cards use ranks `2..9,T,J,Q,K,A` and suits `c,d,h,s`; suits do not break ties. The Java comparator is a separately compiled port of POK's simple five-card reference and best-of-21 approach. It replaces a large external rank data file. For the solver, the base-15 score is negated so smaller ranks are stronger; the diagnostic `evaluate` operation returns the positive score. It is an adapter component, not upstream evaluator provenance.

Utilities are centered zero-sum chips, taking an equal split of the initial pot as baseline. A winner receives half the initial pot plus the opponent's new matched investment; a loser loses half the initial pot plus their own investment. A matched tie is zero. This constant baseline does not affect action comparison, but is different from a screen's current-call-relative EV. Past contributions are not charged again.

Every public decision node exports every retained own-hand combination, including unreachable information sets. Node IDs use stable histories such as `root/CHECK/BET:50`; action labels and child links are explicit. The policy is the normalized upstream accumulated average. `profileEvChips` is an exact weighted sum over compatible hand assignments under that exported policy. Per-combination action EV conditions on the compatible opponent's action reach and then follows both players' exported continuation policies; it is not automatically the equilibrium regret of that action.

`informationSetReach` is the joint probability of the given own hand and public history under the initial compatible weighted distribution and both players' policies. `ownReach` includes the hand's normalized input weight and own actions; `opponentReachMass` sums compatible opponent weights times their actions. Their product divided by `normalizedJointWeight` gives information-set reach. When opponent reach is zero, conditional EV is undefined: the adapter exports a clearly labelled initial-range fallback and zero information-set reach. Such rows must not receive a strategic grade.

`upstreamBestResponseValues` contains each player's exact best-response EV against the other's average policy, using upstream `BestResponse`. In this zero-sum convention:

- NashConv in chips = BR0 + BR1 = the sum of the two unilateral deviation gains.
- Two-player exploitability in chips = NashConv / 2.
- Exploitability as percent of initial pot = NashConv / (2 × pot) × 100.

The raw CLI's `COMPLETE` means only that the requested iterations finished. The application maps it to its own complete/partial state using the requested quality threshold. Float roundoff may produce a tiny negative raw gap; the application permits a narrow rounding tolerance and displays a nonnegative value. A global gap is not a bound on every rare hand's error. Recorded traces sometimes rise between checkpoints; monotone convergence is not claimed.

## Process, memory and input limits

The application uses a fixed approved Java executable and fixed classpath with `shell:false`. The request contains only structured cards, weights, integer tree sizes, and budgets; arbitrary paths, classes, commands and URLs are rejected. Jackson reads a tree, never polymorphic application objects. Duplicate JSON keys, trailing JSON documents, unknown keys, deep nesting, oversized numbers/strings, duplicate cards, impossible ranges and over-budget work fail closed. Stdin is capped at 131,072 bytes, result output at 2,000,000 characters, and parent output at 2,000,000 bytes.

The maximum solve budget is 20,000 iterations, 15 seconds, and one compute thread. The adapter checks the deadline at each complete iteration; an internal 17-second watchdog terminates a stalled request, and the parent also has a timeout. Deadline failure returns no completed strategy. Java flags cap heap at 256 MiB, metaspace at 128 MiB, and code cache at 64 MiB. These alone are not a total-process limit.

`Guard-Solver.ps1` applies a Windows Job Object with a **512 MiB process committed-memory limit** and kill-on-job-close. It verifies the newly spawned PID's executable image and a random per-job ownership token before attaching, and queries the installed limit and flags before emitting READY. The parent withholds the structured request until then. The guard accepts no commands and keeps its stdin open solely as a lifetime signal. Closing the parent/guard job kills only the attached process. OS memory commitment is not the same metric as working-set RAM. Deliberate exhaustion of the 512 MiB allowance was **NOT_RUN**; applying/querying the real OS limit and actual lifetime termination were tested. A job-killed JVM may return exit code zero without a terminal result, so cancellation and absence of a valid result remain failures regardless of exit code.

No system service, firewall, Apache listener, global PATH/JAVA_HOME, Qwen process, account credential, or other user's process was changed. No additional Codex/model session or paid API call was used by this component.

## Verification and limits of the evidence

`node --import tsx engine-adapters/java/verify.ts` ran the real JVM, guard and compiled JAR, producing eight PASS groups in `engine-adapters/java/VERIFICATION.json`: queried job limits; guard-close termination; wrong ownership-token denial; a weighted river with complete normalized policies; structured and generated ranks; a board-playing tie; malformed inputs; and actual short-deadline failure. These are not mocked process tests.

The comparator matched the TypeScript reference on 10,011 five/six/seven-card hands. Separately, PokerKit 0.7.6 checked the actual Java outputs: 10,011 categories and 10,010 adjacent ordering/tie comparisons, zero disagreements, 1.0146 seconds. The corpus has 3,345 five-card, 3,333 six-card and 3,333 seven-card hands. This is generated/structured coverage, not an exhaustive Java census. See `docs/strategy/JAVA_POKERKIT_VERIFICATION.json` and `scripts/java-rank-oracle.py`.

An independent Python sequence-form LP oracle reconstructs all trees, weighted compatibility, PokerKit showdown ranks, and terminal payouts without trusting Java utility output. Six original eight-combination-per-seat scenarios were tested at the predetermined 500, 2,000 and 10,000 iterations, including explicit dead-card blocking and a full raise. All 18 runs against the tested JAR passed the predeclared NashConv ≤ 0.5-chip gate and Java/oracle metric agreement ≤ 0.001 chip. Worst gap among all checkpoints was 0.217977 chip; worst final 10,000-iteration gap was 0.186888 chip. Maximum reported NashConv discrepancy was 0.000011341 chip; maximum conditional node/action EV discrepancy was 0.000003292 chip. Solver-reported compute times ranged from 103.4066 to 307.5666 ms for those small inputs; these exclude process startup and the independent oracle, and are not promises for arbitrary ranges.

The independent checks also cover full policy rows at all nodes, own/opponent/information-set reaches and all terminal values. Zero-opponent-reach fallback rows are excluded from conditional-EV correctness claims. The LP used SciPy 1.18.1/NumPy 2.5.3/PokerKit 0.7.6 in the isolated verification environment, with 1e-8-chip primal/dual tolerance. The complete source-backed evidence is `docs/strategy/SOLVER_QUALITY.json`; original requests/results/oracle files remain in ignored `artifacts/solver-scenarios`. Earlier build evidence was preserved before the final strict-parser fix and rerun. No broader tree, game, production security, public service or mobile execution is certified by these tests.
